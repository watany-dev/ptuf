# Contributing to ptuf

Thank you for considering a contribution. This document covers the
expectations for code, the local development workflow, and the release
mechanics that affect commercial-grade quality.

## Code of Conduct

Be respectful, on-topic, and stay within the project's scope (`docs/design/overview.md`).

## Development Workflow

### Required local checks

Run before every push:

```sh
make check
```

This runs the same gates that block CI:

| Step | What it checks |
| --- | --- |
| `fmt-check` | `cargo fmt -- --check` |
| `lint` | `cargo clippy --all-targets --locked -- -D warnings` |
| `test` | `cargo test --locked` |
| `doc` | `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --locked` |
| `deny` | `cargo deny check advisories licenses bans sources` |

CI additionally runs `tarpaulin` (95% coverage floor), an MSRV `cargo check`
on Rust 1.93.0, `actionlint`, and `cargo-machete`. The MSRV is the floor —
do not raise it without prior discussion.

### Property-Based Testing

`make pbt` runs every `proptest!` block at 10 000 cases (`PROPTEST_CASES`
override available). Run it before tagging a release.

## Commit & PR Hygiene

- One logical change per PR. Mechanical refactors (Tidy First) go in their
  own PRs ahead of the behavioural change.
- Title in imperative mood (`fix:`, `feat:`, `refactor:` etc).
- Include a `test plan` section in the PR body.
- Squash-merge by default.

## Code Style

- `unsafe_code` is forbidden project-wide via `[lints.rust]` in
  `Cargo.toml` and `#![forbid(unsafe_code)]` in `src/lib.rs`.
- `unwrap()` / `expect()` are forbidden in non-test code (warned at lib
  level; integration tests are exempt).
- Public API needs rustdoc (`-D warnings` makes missing docs a build
  failure).

## Cross-Platform Code

`ptuf` targets Linux, macOS, and Windows. When introducing
platform-specific code:

- Use `#[cfg(target_os = "windows")]` (or `unix`/`macos`) at the **module
  or file boundary**, not inline `cfg!(...)` checks.
- Place Windows-only files using the suffix `_windows.rs` or prefix
  `windows*.rs` so `cargo tarpaulin` can exclude them from the
  Linux-only coverage measurement (see `Makefile` and `.github/workflows/ci.yml`).
- Path handling must use `std::path::Path` / `PathBuf`. Never assume
  POSIX separators or case-sensitive comparisons.
- When a test mutates `std::env`, isolate it (`serial_test` or process
  spawn) so tarpaulin can eventually drop `--test-threads=1`.

## Releasing

`ptuf` releases are managed by [`cargo-dist`](https://github.com/astral-sh/cargo-dist).

### Release pipeline

1. Bump `version` in `Cargo.toml` and update `CHANGELOG.md`.
2. `git tag vX.Y.Z && git push --tags`.
3. The `Release` workflow runs `dist plan` → matrix builds across the 5
   supported targets → publishes a GitHub Release with installers.
4. The `Publish to crates.io` workflow then runs `cargo publish --dry-run --locked`,
   followed by `cargo publish --locked` for non-prerelease tags.

### Regenerating `release.yml`

`release.yml` is generated by `dist init` / `dist generate`, but it has
been **manually patched** to:

- Pin all third-party actions to commit SHAs (matches the rest of CI).
- Add a `concurrency` group and request `id-token: write` /
  `attestations: write` for SLSA build provenance.

When you upgrade the `cargo-dist-version` field in `dist-workspace.toml`,
**do not blindly regenerate**. Re-apply the SHA pins and the concurrency
block before committing the regenerated workflow. The header comment in
`release.yml` documents this.

### Bumping cargo-dist

```sh
# 1. Update dist-workspace.toml `cargo-dist-version`.
# 2. Install the matching dist binary locally and regenerate:
dist init  # answer prompts as before
# 3. Re-pin third-party actions (actions/checkout, upload-artifact,
#    download-artifact) to commit SHAs.
# 4. Re-add the concurrency / permissions header.
# 5. Diff against the previous release.yml carefully.
# 6. Run the workflow on a tagged PR to validate.
```
