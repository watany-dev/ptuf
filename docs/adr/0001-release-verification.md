# 0001. Release artifact verification via SHA256SUMS, SPDX SBOM, and GitHub Build Provenance Attestations

- Status: Accepted
- Date: 2026-05-06
- Driver: P0-7
- Related: `docs/RELEASING.md`, `SECURITY.md`, `README.md` "Verified install"

## Context

`ptuf` is a `PreToolUse` guardrail for coding agents. It is downloaded
and installed onto developer machines and CI runners that subsequently
trust its decisions to allow or deny tool invocations. For a tool whose
job is gating other commands on safety, `curl … | sh` (the cargo-dist
default install path documented in `README.md`) is too thin a chain:
it relies on GitHub TLS only — no checksum, no provenance, no signed
manifest of what is being installed.

Concretely, the v0.0.1 release ships:

- `ptuf-<target>.{tar.gz,zip}` for five targets
- `ptuf-installer.{sh,ps1}`
- per-archive `ptuf-<target>.{tar.gz,zip}.sha256` files

There is no aggregate checksum file, no SBOM, and no attestation. A user
who wants to pin a version and verify the binary out-of-band has to
download every per-archive `.sha256` separately and has no Sigstore /
SLSA-style claim that the artifact was built from a specific source
commit by a specific workflow.

This ADR records the design that closes that gap.

## Decision

Add four classes of verification artifacts to every tagged release
(stable and prerelease alike), produced by a new sibling GitHub Actions
workflow `.github/workflows/release-verify.yml` that triggers on
`release: published`.

### What is published

| Artifact | Source | Purpose |
| --- | --- | --- |
| `ptuf-x86_64-unknown-linux-musl.tar.gz` (new) | cargo-dist | Static Linux binary for Alpine / minimal containers |
| `SHA256SUMS` | sibling workflow | Aggregate checksum, `sha256sum -c` compatible |
| `ptuf-<tag>.spdx.json` | Syft (`anchore/sbom-action`) | SPDX 2.3 source SBOM from `Cargo.lock` |
| Build Provenance Attestation | `actions/attest-build-provenance` | Sigstore-backed provenance for archives + `SHA256SUMS` |
| SBOM Attestation | `actions/attest-sbom` | Links the SBOM to each archive |

Verification (recommended in `README.md`):

```bash
sha256sum --ignore-missing -c SHA256SUMS
gh attestation verify <archive> --owner watany-dev
```

### Decisions and rationale

**D1. Sibling workflow rather than hand-patching `release.yml`.**
`release.yml` is regenerated by `dist generate`. The repo's standing
policy (`docs/RELEASING.md`, `release.yml:16-26`) is to keep custom CI
in sibling workflows. A new `release-verify.yml` triggered on
`release: published` follows the same pattern as `publish-crates.yml`,
keeps cargo-dist regeneration friction at zero, and isolates the
verification logic. Trade-off: a brief window between release publish
and verification-asset attachment, mitigated by an operational note in
`README.md` and `SECURITY.md`.

**D2. Add `x86_64-unknown-linux-musl`, keep `x86_64-unknown-linux-gnu`.**
v0.0.1 already promised `aarch64-unknown-linux-gnu` and
`x86_64-unknown-linux-gnu` in `CHANGELOG.md`. Replacing `gnu` with
`musl` would break that contract. Adding `musl` in parallel covers the
static-binary / Alpine demand without rotating filenames out from under
existing users. `musl-tools` is added to `[dist.dependencies.apt]` so
the Linux runner can build the new target.

**D3. GitHub Artifact Attestations (`actions/attest-build-provenance`)
rather than cosign keyless or cargo-dist's built-in SLSA.**
- `gh attestation verify <file> --owner watany-dev` is a single command;
  cosign requires a separate binary plus Rekor URL.
- OIDC keyless ⇒ no key management.
- Decouples our trust anchor from cargo-dist's release cadence (no
  forced 0.31 → 0.32+ bump).
- Adding cosign in the future is non-exclusive; we can layer it on if
  GitHub-independent verification becomes a requirement.

**D4. Repository-level Syft / SPDX SBOM, single file per release.**
Rust's dependency resolution is target-independent, so per-artifact
SBOMs would carry near-identical content with extra noise. SPDX 2.3
JSON is the format `actions/attest-sbom` consumes natively and the one
GitHub treats as a first-class citizen. Syft scans `Cargo.lock`
directly and is the canonical tool that pairs with `attest-sbom`.

**D5. `SHA256SUMS` covers archives + SBOM only; installer scripts are
intentionally excluded.**
The cargo-dist installer scripts are templated and change between
releases. The "verified install" persona reads archives directly; the
"quick install" persona accepts `curl | sh` semantics. Installers are
still covered by build-provenance attestation, just not by checksum
aggregation. Including them in `SHA256SUMS` would invite version
mismatches and add no value to either persona.

**D6. `SHA256SUMS` is built by reading cargo-dist's per-archive
`.sha256` files and concatenating them; SBOM hash is computed
separately because cargo-dist does not produce one.** Reusing
cargo-dist's hashes guarantees row-by-row equality with the per-archive
`.sha256` files cargo-dist already attaches, so users who prefer the
per-archive flow stay consistent.

**D7. README "Verified install" is promoted above "Quick install
(unverified)".** A guardrail tool's flagship onboarding path should
be the verified one. The `curl | sh` convenience path remains, but
under a clearly named "unverified" heading.

**D8. `release-verify` and `publish-crates` run in parallel and do not
block each other.** crates.io publication is immutable and observes
the GitHub Release event independently; coupling the two workflows
adds operational risk (a verification failure freezing crate
publication) without security benefit, since crates.io and GitHub
Releases are separate distribution channels.

**D9. Prereleases are verified identically to stable releases.**
Releasing a `vX.Y.Z-rc.N` exercises the full verification path,
catching musl build issues, attestation permission gaps, and SBOM
schema drift before they reach a stable tag. `publish-crates.yml`
already skips prereleases via `!github.event.release.prerelease`, so
there is no crates.io divergence.

**D10. `release-verify` failure is best-effort.** If
`actions/attest-*` or Syft fails, the GitHub Release stays published;
the workflow surfaces the error in Actions logs and a maintainer
re-runs it. Auto-editing the Release notes or demoting it to draft was
considered and rejected: at the moment a verify failure is detected,
`publish-crates` may already have run, so reverting GitHub state would
diverge from crates.io and damage trust more than it protects. The
maintainer judgement call remains in the loop.

## Consequences

### Positive

- Users on supply-chain-sensitive deployments (regulated CI, hardened
  workstations) have a one-command verification flow that produces
  Sigstore-anchored evidence.
- `SECURITY.md` can point to a concrete verification procedure as part
  of the supported security model.
- Adding `musl` covers the Alpine / distroless / scratch-container
  audience without dropping glibc users.
- `release-verify.yml` is cleanly separable from cargo-dist, so future
  tweaks (cosign signatures, GitHub dependency graph push, SLSA
  manifest) attach to the sibling workflow without touching `release.yml`.

### Negative / known costs

- Three new third-party actions to track for SHA-pin updates
  (`anchore/sbom-action`, `actions/attest-build-provenance`,
  `actions/attest-sbom`). Mitigated by `.github/dependabot.yml`'s
  `github-actions` ecosystem.
- A short post-publish window where the GitHub Release is live but
  `SHA256SUMS` / SBOM / attestations are not yet attached. Documented
  in `README.md` and `SECURITY.md`.
- Verification by `gh attestation verify` requires GitHub CLI 2.49+ on
  the user side; users on older `gh` cannot use that step. Documented
  as a tooling requirement; cosign is left as a possible future
  addition.

### Out of scope

- Cosign keyless signatures (additive, can be layered later).
- Per-artifact / binary-scanning SBOMs.
- `cargo-auditable` embedded SBOMs.
- macOS notarization / codesign.
- Homebrew tap, Scoop bucket, or other third-party package managers.

## Verification

End-to-end testing is performed on a `vX.Y.Z-rc.N` tag prior to a
stable release. The acceptance checklist lives in
`docs/RELEASING.md` and includes:

- All six target archives build, including `x86_64-unknown-linux-musl`.
- `release-verify.yml` succeeds and attaches `SHA256SUMS` and the SBOM.
- `gh attestation verify` succeeds for archives and `SHA256SUMS`.
- `sha256sum --ignore-missing -c SHA256SUMS` succeeds.
- The `README.md` "Verified install" recipe runs cleanly in a fresh
  `ubuntu:22.04` container and `ptuf --version` prints the tag.
